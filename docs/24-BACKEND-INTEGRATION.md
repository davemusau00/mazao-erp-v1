The deployed administration/configuration gaps are recorded in [the server configuration gap report](26-SERVER-CONFIGURATION-GAPS.md). Manage has authoritative business/outlet/tax/receipt/capability settings, outlet creation/editing/safe deactivation and computed setup checks. Authenticated outlet context switching is implemented at source; isolated database and browser acceptance remain open. Physical terminal pairing remains outstanding. The application requires server authentication in every build and has no reachable preview workspaces.

This register describes the actual authenticated API boundary. An unsubmitted draft is not committed state, an outbox row is not remote delivery, and a cash command is not a card or mobile-money provider confirmation. All reachable workspaces use server records; archived prototype code has no runtime authority.

## Runtime and first operator

The API is a Fastify modular monolith at `apps/api/src/server.ts`; PostgreSQL is required through `DATABASE_URL`. The Vite development server proxies `/api/v1` to `http://127.0.0.1:4101`. Production needs TLS termination and an explicit API route. Do not expose the development bind address publicly.

1. Start PostgreSQL and provide `DATABASE_URL` (optionally `DATABASE_SSL=require` and `DB_POOL_SIZE`).
2. Run `npm run db:migrate`. The runner applies all checked-in checksummed migrations in order (currently through 028), performs required compatibility repairs, and verifies checksums for already-applied versions. Use the runner; applying SQL files manually bypasses these repairs.
3. From a private interactive terminal, run `npm run api:bootstrap`. Type the confirmation phrase, enter business, first-outlet and owner details, and enter the owner password at the hidden prompt. The script refuses non-interactive use and refuses `ADMIN_PASSWORD` in the process environment. It creates random tenant/outlet/owner/workspace IDs in one transaction, hashes the owner password, and prints no password. It only creates the first tenant in an empty business database. Save the displayed bootstrap request ID; if the response is lost, rerun with `BOOTSTRAP_REQUEST_ID=<same UUID>` and the same setup details to retrieve the original IDs without creating duplicates or changing the password. New tenants start in `SETUP`; the owner uses Manage: Setup checklist to finish saved readiness checks and record a reasoned go-live review before ordinary sales and finance work is enabled. The initial workspace is a logical assignment; physical terminal enrollment remains separate S02-04 work.
4. Run `npm run api:dev` and `npm run dev`. Use **Sign in to Mazao**. Login requires a valid password, an active membership, and at least one active outlet/workspace assignment. Credentials are verified before the server returns authorized assignment choices; a user with multiple active assignments selects one after authentication. A signed-in operator can use **Switch workspace** to select another active assignment owned by that same account.

`APP_ORIGINS` is an exact-origin allowlist for unsafe methods and is required at API startup in production. Production unsafe requests without an Origin or with an origin outside the allowlist are denied. `CREDENTIAL_FINGERPRINT_KEY` is also required for staff credential changes; configure a persistent 64-hex-character secret generated with `openssl rand -hex 32` (see [the environment template](../infra/.env.example)). Keep it stable across restarts and releases. `SESSION_HOURS` defaults to 12. Session cookies are HttpOnly and SameSite Strict, Secure in production, with a CSRF cookie/header pair. User, membership, device, onboarding status and session are rechecked on every request. Pending setup sessions can reach only setup routes; ordinary business reads and commands are denied by the API until the owner review is committed. Login throttling is per process; multi-replica deployments need a shared gateway limiter. Keep secrets out of source control. `MIGRATION_TARGET` is a migration-test aid that stops the runner after the named version. Use it only with a disposable acceptance database; ordinary setup and operations should leave it unset so all migrations are applied.

## HTTP and command contracts

Routes use `/api/v1`; JSON errors have `{ error: { code, message } }` shape. The browser adapter is `src/services/apiClient.ts`. Authenticated routes use the server session to select tenant, outlet, operator, device, role and capabilities; caller-supplied tenant or actor values do not grant authority.

| `GET /health/ready` | Public | Confirms PostgreSQL connectivity only. |
| `POST /auth/login` | Public, rate limited | Password verification, active membership/device resolution, server session and CSRF cookies. |
| `GET /auth/me` | Session | Current user, server-issued role permissions, tenant, currency, tenant time zone, tax policy, capabilities, outlet with its own time zone, and device. Login returns the same identity shape. |

| `POST /auth/logout` | Session + CSRF | Revokes the current session. |
| `GET /catalog/items` | Session + catalog, inventory receive, count or sell role | Tenant/outlet product and balance snapshot. Quantity is a decimal string; money is integer minor units. `costPriceMinor` is returned only to `catalog.manage` or `finance.view` permissions. |

| `GET /hospitality/stays` | Session + hospitality capability + front desk/manage role | Active stays and an estimate based on booked nights and the stored tax-rate snapshot. |
| `POST /commands` | Session + CSRF | Idempotent command receipt; the canonical stored outcome is returned unchanged on exact replay. Domain mutation, audit and outbox are one serializable transaction. |
| `GET /commands/:commandId` | Session | Tenant-scoped command status and stored outcome for unknown-result recovery. |

Command envelope: `{ protocolVersion: 1, commandId, tenantId?, deviceId, type, occurredAt, expectedVersions, payload }`. The authenticated session determines authority. Reusing a command ID with different content is rejected. Domain errors are durably recorded as `REJECTED` or `CONFLICT`; confirmed outcomes are retained. Exact replay returns the same outcome shape and does not run the mutation again. On transport failure, retain the ID and check status before retrying.

Cash sale tender values express cash handed over; only the amount due is recorded as payment, with excess returned as change. Active customer accounts may be charged in full within their server-approved credit limit. Cash is the only confirmed repayment/refund tender. Card and M-Pesa remain rejected until a provider can verify them; cash/account mixed tender is unsupported. Money is integer minor units, quantities are decimal strings (six places maximum), and tax is stored as basis points. Outlet time zone determines hotel business-date checks.

Finance report dates use the authenticated outlet's IANA time zone; scope is explicitly tenant-wide because the current journal is not outlet-scoped. Trial balance checks only whether available journal entries balance with each other; it does not reconcile cash, inventory, subledgers or external statements. The operating summary includes recognized posted account codes and identifies unclassified accounts plus omitted supplier invoices/AP and operating expenses, payroll/accrual, depreciation, provider settlement and period-close sources. Customer AR is journaled, but a full subledger-to-control reconciliation is not implemented. Period controls, complete financial statements, and approval/close commands are not implemented.

Hotel checkout is deliberately narrow: the current command settles the booked room nights in full for cash and does not support deposits, ancillary charges, split folios, partial balance, early-departure recalculation or payment-provider confirmation. It must not be represented as the full hotel folio lifecycle from `docs/11-HOSPITALITY.md`.

## UI connection state

- **Today** uses the authenticated tenant/outlet/operator and current server shift. It does not include local demo sales or stock figures.
- **Sell** fetches the server catalog and shift. Once signed in, it cannot fall through to `storage.processSale` when the catalog is unavailable; server checkout is disabled until catalog, shift and authorized customer account data load. Cash or an approved customer account are accepted. Unknown results retain the command in IndexedDB and offer status recovery.
- **Sales history** loads outlet orders from the API. Authorized managers can refund eligible line quantities for cash and choose whether returned stock is restored. Provider reversals, refund approvals and immutable receipt documents are not connected.
- **Stock** loads server catalog/movements and supports item setup. Its **Receive stock** action opens the reviewed delivery form in Purchasing. The separate **Count stock** workspace persists a full outlet baseline and draft across reloads; storekeepers save lines and manager roles review/post or cancel. Posting checks baseline balance versions and records movements plus a balanced variance journal. The optional area label is descriptive only; no physical locations exist. Supplier text and document references are evidence only; supplier masters, purchase orders and accounts payable are not implemented.
- **Shifts** uses server open/close and paid-in/payout commands with current shift state and movement history. Payout requires manager-level `shift.payout`; cashiers cannot call it. Close recomputes the drawer from shift cash sources, fails closed on a mismatch, and creates an immutable cash Z report; operators see their own reports and `finance.view` roles see outlet history. Expense/supplier classification, supervisor approval, non-cash tender coverage and full sales/tax Z reporting remain absent.
- **Hotel and Reservations** use the authenticated room, reservation and stay queries with idempotent server commands. Front desk can create/cancel reservations and check in/check out; housekeeping can mark dirty rooms ready. Checkout limits are listed above. No workspace opens without an authenticated session.
- **Navigation** filters by current server role and tenant capability. In server mode, authorized finance users can open server-backed reports and users with customer permissions can open the connected account workspace; Manage is available under config.view/config.manage; unsupported food service and separate onboarding provisioning remain unavailable. Stock count is connected for authorized users.
- An unresolved command shows its recovery action. A status `404` means no server command record exists; only then may the same retained command ID be resent. A confirmed status displays the stored outcome.

## Customer receivables integration (migration 012)

The authenticated Customers workspace now lists tenant-scoped accounts, presents charge/repayment statements, and supports manager account setup. POS cashiers with `customers.charge` may charge an active account only when the server confirms the account balance plus sale is within its approved limit. The browser PIN demo does not grant server authority.

- `GET /customers` and `GET /customers/:customerId/statement` require `customers.view` and the commerce capability. The statement combines confirmed sale charges and repayment allocations, verifies each repayment allocation sum, and rejects a computed balance that differs from the account control balance.
- `customers.account.create` and `customers.account.update` require `customers.manage`; updates use `customer:<id>` versions.
- `sales.order.settle` with `customerId` requires `customers.charge`, no cash tenders, and the current `shift:<id>` version. It posts the sale to ACCOUNTS_RECEIVABLE, snapshots the customer name/due on the receipt, records the charge, and advances the account and shift versions atomically.
- `customers.repayment` requires `customers.settle`, an open operator shift and its version. It accepts cash only, rejects amounts above the balance, allocates oldest outstanding charges first, reduces AR, posts CASH_TILL against ACCOUNTS_RECEIVABLE, and increases expected drawer cash plus the separate customer-collection total.
- Cash receipt evidence is an operator-confirmed cash command. M-Pesa/card collection is rejected until a provider confirms it. Customer credit-sale refunds are blocked pending account-credit and tax-aware reversal policy. Mixed cash/account tender, aging, statement export, supplier AP and full subledger reconciliation remain out of scope.
