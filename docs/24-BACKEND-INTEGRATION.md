# Backend integration register (v1 foundation)

This register describes the actual authenticated API boundary. Browser demo storage is not a backend; a local draft is not committed state; an outbox row is not remote delivery; and a cash command is not a card or mobile-money provider confirmation.

## Runtime and first operator

The API is a Fastify modular monolith at `apps/api/src/server.ts`; PostgreSQL is required through `DATABASE_URL`. The Vite development server proxies `/api/v1` to `http://127.0.0.1:4101`. Production needs TLS termination and an explicit API route. Do not expose the development bind address publicly.

1. Start PostgreSQL and provide `DATABASE_URL` (optionally `DATABASE_SSL=require` and `DB_POOL_SIZE`).
2. Run `npm run db:migrate`. The runner applies checksummed migrations `001_initial` through `010_composite_tenant_foreign_keys` in order. Before an unapplied migration 003, it normalizes the original generated order-status constraint name to the name expected by that migration. Before unapplied migration 004, it creates the missing `hospitality` schema. Migration 010 validates tenant/outlet-scoped relationships for device assignments, shifts, orders, order lines, payments and journal records; it fails closed if existing records cross those boundaries. Already-applied versions are checksum checked and these compatibility steps are skipped. Use the runner; applying SQL files manually bypasses these repairs.
3. Set `BOOTSTRAP_CONFIRM=CREATE_INITIAL_TENANT`, `TENANT_NAME`, `TENANT_CURRENCY`, `TENANT_TIME_ZONE`, `OUTLET_NAME`, `OUTLET_TIME_ZONE`, `ADMIN_EMAIL`, `ADMIN_NAME`, `ADMIN_PASSWORD` (12+ characters), and `DEVICE_LABEL`; then run `npm run api:bootstrap` once. `TENANT_CAPABILITIES` is a comma-separated list and defaults to `retail,inventory,commerce`; include `hospitality` to enable hotel routes and commands. Bootstrap stores a scrypt password hash and prints generated IDs, never the password.
4. Run `npm run api:dev` and `npm run dev`. Sign in through **Connect backend**. Login requires one active membership and one active outlet/device assignment for the account.

`APP_ORIGINS` is an exact-origin allowlist for unsafe methods and is required at API startup in production. Production unsafe requests without an Origin or with an origin outside the allowlist are denied. `SESSION_HOURS` defaults to 12. Session cookies are HttpOnly and SameSite Strict, Secure in production, with a CSRF cookie/header pair. User, membership, device and session are rechecked on every request. Login throttling is per process; multi-replica deployments need a shared gateway limiter. Keep secrets out of source control.

## HTTP and command contracts

Routes use `/api/v1`; JSON errors have `{ error: { code, message } }` shape. The browser adapter is `src/services/apiClient.ts`. Authenticated routes use the server session to select tenant, outlet, operator, device, role and capabilities; caller-supplied tenant or actor values do not grant authority.

| Route | Authorization | Behavior |
| --- | --- | --- |
| `GET /health/live` | Public | Process liveness only. |
| `GET /health/ready` | Public | Confirms PostgreSQL connectivity only. |
| `POST /auth/login` | Public, rate limited | Password verification, active membership/device resolution, server session and CSRF cookies. |
| `GET /auth/me` | Session | Current user, server-issued role permissions, tenant, currency, tenant time zone, capabilities, outlet and device. Login returns the same identity shape. |
| `POST /auth/logout` | Session + CSRF | Revokes the current session. |
| `GET /catalog/items` | Session + catalog, inventory receive, count or sell role | Tenant/outlet product and balance snapshot. Quantity is a decimal string; money is integer minor units. `costPriceMinor` is returned only to `catalog.manage` or `finance.view` permissions. |
| `GET /inventory/movements` | Session + inventory receive role | Latest 250 tenant/outlet movements with quantity delta and balance evidence. |
| `GET /inventory/counts` | Session + `inventory.count` or `inventory.count.approve` | Latest 50 outlet count summaries, including state and completion. |
| `GET /inventory/counts/current` | Session + count permission | Open full outlet count with baseline snapshot and saved count lines. |
| `GET /inventory/counts/:countId` | Session + count permission | Tenant/outlet-scoped count history and line-level before/count/reason evidence. |
| `GET /shifts/current` | Session + shift open/close/payout role | Current operator's open shift, expected drawer balance, version and recent paid-in/payout evidence. |
| `GET /sales/orders` | Session + sell, refund or finance role | Latest 250 outlet orders with line, tender and refund totals. `costPriceMinor` is included per line only with `finance.view`. |
| `GET /reports/trial-balance?asOf=YYYY-MM-DD` | Session + `finance.view` | Tenant-wide posted journal trial balance through the selected outlet business date, integer-minor totals, journal balance checks and source counts. |
| `GET /reports/profit-loss?from=YYYY-MM-DD&to=YYYY-MM-DD` | Session + `finance.view` | Tenant-wide `PARTIAL_OPERATING_SUMMARY` with recognized account lines, unclassified accounts and omitted-source coverage; it is not a complete P&L or net-profit result. |
| `GET /reports/journal-lines` | Session + `finance.view` | Tenant-scoped, paginated journal-source detail by account and either `asOf` or a date range (maximum 367 days). |
| `GET /hospitality/rooms` | Session + hospitality capability + hotel view role | Outlet room status, rate snapshot and active guest summary. |
| `GET /hospitality/reservations` | Session + hospitality capability + front desk/manage role | Confirmed reservations for the outlet. |
| `GET /hospitality/stays` | Session + hospitality capability + front desk/manage role | Active stays and an estimate based on booked nights and the stored tax-rate snapshot. |
| `POST /commands` | Session + CSRF | Idempotent command receipt; the canonical stored outcome is returned unchanged on exact replay. Domain mutation, audit and outbox are one serializable transaction. |
| `GET /commands/:commandId` | Session | Tenant-scoped command status and stored outcome for unknown-result recovery. |

Command envelope: `{ protocolVersion: 1, commandId, tenantId?, deviceId, type, occurredAt, expectedVersions, payload }`. The authenticated session determines authority. Reusing a command ID with different content is rejected. Domain errors are durably recorded as `REJECTED` or `CONFLICT`; confirmed outcomes are retained. Exact replay returns the same outcome shape and does not run the mutation again. On transport failure, retain the ID and check status before retrying.

| Command | Permission / capability | Required input and expected versions | Committed effects |
| --- | --- | --- | --- |
| `catalog.product.create` | `catalog.manage` | SKU, name, base unit, tenant currency, integer sell/cost minor units, tax basis points | Product, zero stock balance, audit and outbox. |
| `inventory.receive` | `inventory.receive` | Product lines with decimal quantity strings and integer unit cost; optional supplier text and delivery reference | Locks products, increases quantity and weighted-average carrying value, writes immutable receipt quantity/value evidence, balanced inventory/accrual journal, audit and outbox. |
| `inventory.count.open` | `inventory.count` | Optional descriptive area label; no expected version for a new session | Locks outlet balances, snapshots active item quantities/versions/carrying values plus the reference-cost fallback, creates a durable full-count draft, audit and outbox. One open full count per outlet. |
| `inventory.count.save` | `inventory.count` | Count ID and every line's nullable decimal quantity/optional reason; expected `count:<id>` version | Saves draft lines and actor/time evidence; advances count version, audit and outbox. |
| `inventory.count.post` | `inventory.count.approve` | Count ID; expected `count:<id>` version | Requires every item counted and variance reasons, rejects catalog/balance changes, applies all differences at the snapshot weighted-average value (using reference cost only when baseline stock is zero), records immutable quantity/value `COUNT_ADJUSTMENT` movements and a balanced variance journal, marks posted, audit and outbox. |
| `inventory.count.cancel` | `inventory.count.approve` | Count ID; expected `count:<id>` version | Version-checks and cancels an open draft without changing stock; preserves history, audit and outbox. |
| `shift.open` | `shift.open` | Opening float minor units | One open operator/outlet shift, opening journal if nonzero, audit and outbox. |
| `shift.cash.movement` | `shift.payout` | Open shift, `PAID_IN` or `PAYOUT`, positive amount in minor units, reason; expected key `shift:<id>` | Locks and versions the shift, applies drawer delta, rejects a payout above expected cash, records immutable movement evidence, posts a balanced clearing journal, audit and outbox. Clearing accounts do not classify supplier or operating expenses. |
| `shift.close` | `shift.close` | Shift ID, counted cash; expected key `shift:<id>` | Version-checked close and variance journal, audit and outbox. |
| `sales.order.settle` | `commerce.sell` | Product lines, cash tender allocations and `shift:<id>` | Checks stock and tender coverage, allocates sale COGS from locked inventory carrying value using moving weighted average, snapshots exact line COGS, consumes quantity/value, records cash allocation, advances shift, audit and outbox. |
| `sales.order.refund` | `commerce.refund` (admin/owner/manager) | Order, reason, return lines and `shift:<id>` | Locks original order/lines, caps returned quantity, apportions original subtotal/tax/COGS snapshots, requires available drawer cash, optionally restores quantity and exact returned COGS value, posts VAT-aware reversals, audit and outbox. |
| `hotel.room.create` | `hotel.manage` + `hospitality` | Room number/type, positive nightly rate, tax basis points | Tenant-currency room and audit/outbox. |
| `hotel.reservation.create` | `hotel.frontdesk` + `hospitality` | Room, guest, date range and expected `room:<id>` version | Checks overlaps under a serializable transaction, creates reservation, advances room version to serialize competing availability changes, audit/outbox. |
| `hotel.reservation.cancel` | `hotel.frontdesk` + `hospitality` | Reservation and expected `reservation:<id>` version | Cancels confirmed reservation, advances room version, audit/outbox. |
| `hotel.checkin` | `hotel.frontdesk` + `hospitality` | Reservation or walk-in details; expected room and reservation versions | Checks outlet-local business date and availability, creates stay and open folio, occupies room, advances versions, audit/outbox. Walk-ins must start on the current outlet business date. |
| `hotel.checkout` | `hotel.frontdesk` + `hospitality` | Stay, cash tender/currency, current shift; expected stay, room and shift versions | On/after booked departure date, settles booked nights by cash, posts room revenue/VAT/cash, closes folio/stay, dirties room, advances shift, audit/outbox. |
| `hotel.room.mark_ready` | `hotel.housekeeping` + `hospitality` | Dirty room and expected `room:<id>` version | Marks room ready, records housekeeping event, audit/outbox. |

Sale tender values express cash handed over; only the amount due is recorded as payment, with excess returned as change. Cash is the only confirmed sale/refund tender. Card, M-Pesa and mixed-provider settlement remain rejected until a provider can verify them. Money is integer minor units, quantities are decimal strings (six places maximum), and tax is stored as basis points. Outlet time zone determines hotel business-date checks.

Finance report dates use the authenticated outlet's IANA time zone; scope is explicitly tenant-wide because the current journal is not outlet-scoped. Trial balance checks only whether available journal entries balance with each other; it does not reconcile cash, inventory, subledgers or external statements. The operating summary includes recognized posted account codes and identifies unclassified accounts plus omitted AP, AR, operating expenses, payroll/accrual, depreciation, provider settlement and period-close sources. Period controls, complete financial statements, and approval/close commands are not implemented.

Hotel checkout is deliberately narrow: the current command settles the booked room nights in full for cash and does not support deposits, ancillary charges, split folios, partial balance, early-departure recalculation or payment-provider confirmation. It must not be represented as the full hotel folio lifecycle from `docs/11-HOSPITALITY.md`.

## UI connection state

- **Today** uses the authenticated tenant/outlet/operator and current server shift. It does not include local demo sales or stock figures.
- **Sell** fetches the server catalog and shift. Once signed in, it cannot fall through to `storage.processSale` when the catalog is unavailable; server checkout is disabled until both catalog and shift state load. Cash is the only accepted tender. Unknown results retain the command in IndexedDB and offer status recovery.
- **Sales history** loads outlet orders from the API. Authorized managers can refund eligible line quantities for cash and choose whether returned stock is restored. Provider reversals, refund approvals and immutable receipt documents are not connected.
- **Stock** loads server catalog/movements and supports item setup. Its **Receive stock** action opens the reviewed delivery form in Purchasing. The separate **Count stock** workspace persists a full outlet baseline and draft across reloads; storekeepers save lines and manager roles review/post or cancel. Posting checks baseline balance versions and records movements plus a balanced variance journal. The optional area label is descriptive only; no physical locations exist. Supplier text and document references are evidence only; supplier masters, purchase orders and accounts payable are not implemented. Local preview has Add item and Add stock actions, but they write browser preview data only.
- **Shifts** uses server open/close and paid-in/payout commands with current shift state and movement history. Payout requires manager-level `shift.payout`; cashiers cannot call it. Movements post to clearing accounts. Expense/supplier classification, counted-cash reconciliation, supervisor approval and a complete Z report remain absent.
- **Hotel and Reservations** use the authenticated room, reservation and stay queries with idempotent server commands. Front desk can create/cancel reservations and check in/check out; housekeeping can mark dirty rooms ready. Checkout limits are listed above. The old preview remains active only when no backend session exists.
- **Navigation** filters by current server role and tenant capability. In server mode, authorized finance users can open server-backed reports; unsupported food service, customer credit, manage and onboarding screens stay hidden. Stock count is connected for authorized users.
- An unresolved command shows its recovery action. A status `404` means no server command record exists; only then may the same retained command ID be resent. A confirmed status displays the stored outcome.

The outbox is written in the same transaction as connected commands, but no worker publishes it. It does not mean remote synchronization. `/health/ready` checks only PostgreSQL. High-risk commands are online-only. Role permissions are coarse server role maps rather than tenant-specific grants.

## Integrity, security and acceptance status

The migration runner keeps applied SQL checksums immutable. Its targeted compatibility preparation addresses the known 003 constraint-name mismatch and 004 missing-schema issue only before those versions are first applied. Hosted CI run [38544946257](https://github.com/davemusau00/mazao-erp-v1/actions/runs/38544946257) succeeded for commit `448865f` (nine migrations); the earlier run [38458774590](https://github.com/davemusau00/mazao-erp-v1/actions/runs/38458774590) remains a historical failure on the quantity-string expectation. The current worktree adds migration 010 after that hosted run. On 14 October, local acceptance applied migrations 001–010 to both a populated upgrade database and a fresh PostgreSQL 16 database; a second fresh-database run verified all ten checksums. `npm run test:api` passed 9 tests (0 failed, 0 skipped) on both populated and fresh databases. New direct-SQL adversarial cases prove that cross-tenant device assignment, order shift, order line, payment, journal-line and order-operator references are rejected by PostgreSQL. Existing acceptance covers authenticated catalog and cost redaction, exact replay, two-cost receipts and carrying value, full-outlet count save/replay/role/reason/post/journal/conflict/cancel, weighted-average sale COGS and journal, partial cash refund and restored carrying value, tenant rejection, paid-in/payout, shift close, reservation contention, SQLSTATE retry fault injection, hotel lifecycle, hostile print-helper input and production-origin checks. Retry coverage uses synthetic SQLSTATE faults rather than natural SSI/deadlock contention; the hotel test advances stay dates in SQL. `npm run typecheck` passed; the production build is 689.72 kB for the main JS chunk and reports the existing Vite `__dirname` and chunk-size warnings. CI has not run migration 010 or its new adversarial cases. Browser journeys, physical printer acknowledgement, production deployment and backup/restore were not tested.

### Finance report verification (14 October)

`npm run typecheck`, `npm run build`, and `npm run test:api` pass for the current local worktree. The API suite passed 9 tests (0 failed, 0 skipped) on PostgreSQL 16 migrated through 010. It verifies report dates, balanced trial-balance output, the explicit partial-summary contract, journal account drill-through and cashier denial. Hosted CI run 38544946257 predates migration 010 and these report changes. The production build still reports the existing Vite `__dirname` warning and a main JavaScript chunk above 500 kB. Browser layout and assistive-technology acceptance have not been run.

Known remaining risks include no complete inventory valuation/report reconciliation or complete financial statement/period-close verification, coarse role maps instead of tenant grants, non-composite actor/event references outside the hardened core order/payment/journal paths, no provider-backed tenders, no outbox worker, no server-side approval grants, and no browser end-to-end acceptance. The product setup cost is a fallback/reference value, not sales COGS. Do not treat the API slice as production-ready or claim the ERP implementation complete.
